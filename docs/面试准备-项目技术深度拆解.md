## 一、事实决策 + AI 解释分层架构

**简历原文：**
> 设计事实决策 + AI 解释分层架构，将院校筛选、档位判定及候选排序等客观决策逻辑交由规则引擎执行，大模型仅负责推荐理由生成与风险分析。

### 技术实现

```
┌─ 规则引擎层（确定性，不依赖 AI）─────────────────┐
│                                                 │
│  SQL 12表联查 → RowMap → SchoolFact             │
│  gap = 估分 - 均分                              │
│  classifyTier(gap, canBeSafe) → reach/steady/safe│
│  policyScore 综合排序（数据完整度+名额风险+层次+gap)│
│  486所 → 候补池 30-60所                         │
│                                                 │
│  ← 这部分永远正确，不靠 AI                        │
└─────────────────────────────────────────────────┘
                    ↓
┌─ AI 解释层（非确定，但结果被校验）─────────────────┐
│                                                 │
│  DeepSeek 收到：候选人事实卡（不含规则推理结果）     │
│  AI 返回：JSON [{programId, reason, risks, pros}]│
│  → 5层校验                                      │
│  → 写入草稿                                      │
│                                                 │
│  ← AI 只做"精选+解释"，不做"海选+决策"             │
└─────────────────────────────────────────────────┘
```

### 面试话术

> "择校推荐有个核心矛盾：你希望推荐结果是客观可信的，但你又希望 AI 能给每所学校写一段个性化的分析理由。如果让 AI 从 400 多所学校里直接推荐，它可能编造学校、编造分数线、或者推荐一堆不在你目标地区的学校——这些都是幻觉。
>
> 我的做法是把推荐拆成两层。底层是规则引擎，SQL 联查 12 张表，用 gap 分差、名额风险、学校层次这些客观指标做筛选和排序，这部分是确定性的、可审计的。上层是 AI 解释，我把规则引擎筛出来的 30 所候选池发给 AI，让它从中精选 3-4 所并写推荐理由。但 AI 的返回不是直接用的——过 5 层校验，万一它编了一个不在候选池里的学校 ID，直接拦截标记为幻觉。
>
> 这样推荐结果是规则引擎保证的，但用户看到的是 AI 写的个性化分析。"

### 追问应对

**Q: "规则引擎具体是怎么分档的？"**

```java
// SchoolFact.classifyTier()
gap = 用户估分 - 学校平均录取分

gap ∈ [-15, 5]   → reach  (冲刺档: 分差接近或略低于录取线)
gap ∈ [6, 14]    → steady (稳妥档: 有一定优势)
gap ≥ 15 + 名额充足 + 数据完整 → safe (保底档)
gap < -15        → 排除（差距太大无意义）
```

**Q: "为什么不让 AI 做所有事情，非要分层？"**

> 两个原因。第一是幻觉：AI 确实会编造学校和分数线。第二是可解释性：如果用户问"为什么推荐这所学校"，规则引擎能给出 gap 分差、录取名额、数据来源这些客观依据，而 AI 只能给一个文本理由，背后没有数据支撑。

## 二、四阶段候选池构建

**简历原文：**
> 设计"数据库过滤 → 规则引擎筛选 → 综合排序 → AI 精选"四阶段候选池构建流程，基于分差、招生规模、院校层次、数据完整度及用户偏好等维度计算综合得分，将 486 所院校缩减至 30~60 所候选池。

### 技术实现

```
486 所 (DB 中全部 408 专业)
  ↓
┌─ 阶段1: DB 过滤 (RecommendationMapper.selectCandidates) ─┐
│ 12 表 LEFT JOIN: program → college → school →             │
│ program_subject → admission_score → admission_plan →      │
│ admission_result → data_quality → data_source ×3         │
│                                                            │
│ WHERE: is_408=1, full_time, subject_codes='101,201,301,408'│
│        province/city IN ('福建'), gap ≥ -30, LIMIT 300    │
│ → 约 100-300 行原始数据                                    │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 阶段2: 规则引擎筛选 (CandidateUniverseServiceImpl) ──────┐
│ RowMap → SchoolFact.fromRow()                             │
│   gap = estimatedScore - avgAdmittedScore                 │
│   gap < -30 → 排除（差距过大）                              │
│   canBeSafe = 名额≥10 + 数据完整 + 录取分范围合理          │
│   classifyTier(gap, canBeSafe) → reach/steady/safe        │
│                                                            │
│ → 约 50-80 所 (Universe)                                   │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 阶段3: 综合排序 (CandidateWorkspaceServiceImpl) ─────────┐
│ 排除 dataCompleteness == "C"                               │
│ diversityTrim: 同校只保留最高分的 1 个专业方向              │
│                                                            │
│ policyScore =                                              │
│   数据完整度 (A=30, B=20, C=10)                             │
│   + 名额风险 (normal=30, medium=20, high=10)               │
│   + 学校层次 (985=25, 211/双一流=18, 其他=10)              │
│   + gap适配度 (max(0, 15 - |gap - idealGap|))             │
│   + 偏好加权:                                              │
│       学校层次优先 → 985+9分, 211+8分                      │
│       发达地区优先 → 发达城市 +14分                         │
│       安全上岸优先 → gap加分 + 名额加分                     │
│                                                            │
│ LIMIT 30 per tier → 3档 × ≤30 = 候选池                     │
│ → 约 30-60 所 (Workspace)                                  │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 阶段4: AI 精选 (AiSelectorServiceImpl) ──────────────────┐
│ 每档从 Workspace 中精选:                                    │
│   reach ≤ 3 / steady ≤ 4 / safe ≤ 3                       │
│ → 最终草稿 ≤ 10 所                                          │
└────────────────────────────────────────────────────────────┘
```

### 面试话术

> "候选池构建是最核心的设计决策。我的思路是：不让 AI 从 400 多所学校里海选，而是先用规则引擎筛出一个 30-60 所的候选池，AI 只负责从这个候选池里精选。
>
> 规则引擎做了四件事：第一，SQL 12 表联查把专业信息、录取分数、招生名额这些散落在不同表里的数据拼成一张完整画像。第二，用 gap 分差给每所学校打上 reach/steady/safe 标签。第三，用综合评分排序——不是简单的分差排序，而是一个加权算法，把数据完整度、名额风险、学校层次、gap 适配度都算进去，还有用户偏好（你选发达地区优先，那北京上海的学校就加 14 分）。第四，diversity trim——同一所学校如果有三个计算机相关专业，只保留评分最高的那个，保证候选池里有不同学校的选择。
>
> 这样 AI 拿到的不是 400 所学校的海量数据，而是 30 所精选过的候选池，每所学校只有一行事实卡文本。上下文长度从几万 token 压缩到几百 token，幻觉概率也被大幅降低。"

### 追问应对

**Q: "为什么排序逻辑从 SQL 移到 Java？"**

> SQL 排序只能单维度（ORDER BY ABS(gap)），而且 12 表 JOIN 的结果集做 filesort 代价很高。Java 层可以做多维加权排序，还能根据用户偏好动态切换排序策略——发达地区优先、学校层次优先、安全上岸优先三种模式，SQL 做不到这种灵活度。

**Q: "DiversityTrim 为什么同校只保留一个专业？"**

> 避免一个学校 3 个专业全部霸占候选池。如果厦门大学有计算机科学、计算机技术、人工智能三个方向都进了候选池，AI 大概率三个都选，其他学校就没了机会。保留评分最高的一个，既保证了候选池的多样性，又不会漏掉好学校。

## 三、五层校验 + 四层降级

**简历原文：**
> 设计"五层校验 + 四层 Fallback 降级"机制，通过候选池约束、幻觉 ID 拦截、去重校验、数据完整度过滤及档位裁剪实现推荐结果治理；针对超时、网络异常及 JSON 解析失败等场景自动降级。

### 技术实现

**五层校验 (SelectionValidator.java)：**

```
AI 返回 JSON:
[{"programId":1001,"reason":"..."}, {"programId":9999,"reason":"..."}]
  ↓
L1: null ID 检测    → programId 为空？     → 拦截："programId 为空"
L2: 池外检测        → programId 不在候选池？ → 拦截："AI 幻觉已拦截"（最关键）
L3: 去重检测        → 同一 ID 重复出现？    → 拦截："候选重复，已去除"
L4: 数据完整度过滤   → dataCompleteness==C？ → 拦截："不具备推荐条件"
L5: 档位上限裁剪    → 超过 3(reach)/4(steady)/3(safe) → 溢出拦截
  ↓
干净结果 → 写入草稿
```

**四层降级 (AiSelectorServiceImpl.select())：**

```
├─ 候选为空        → 空结果（不调 AI）
├─ 调用失败/超时   → selectAll：取 top-N 候选 + 自动生成理由
├─ AI 返回空/null  → selectAll
└─ JSON 解析失败   → selectAll
      │
      └─ DraftServiceImpl 层还有第 4 层:
         CompletableFuture.orTimeout(90s).exceptionally()
         → fallbackTierResult(): 不调 AI，直接取候选池 top-N
         → 标记 fallback=true → 前端显示"数据匹配度自动选择"
```

### 面试话术

> "AI 是不可靠的，我做了两层防御。第一层在 AI 调用层：超时、网络错误、返回格式错误——任何一种失败都会降级到基于数据评分的机器选择，用户永远看不到错误页面。
>
> 第二层在校验层。即便 AI 成功返回了 JSON，也不代表这 JSON 能用。比如 AI 可能编造一个不存在的学校 ID（幻觉），可能把同一个学校推荐两次（重复），可能推荐数据不完整的学校（比如只有名字没有录取分数）。我的 validator 逐项检查，每一项不合格就拦截并记录原因。所有 BLOCKED 的候选都会持久化，用户可以审计 AI 到底推荐了什么、为什么被拦截。
>
> 面试官问"你凭什么相信 AI 的推荐结果是可靠的"——我的回答是"我不相信，所以我做了 5 层校验"。这就从技术问题变成了架构自信。"

### 追问应对

**Q: "降级后的机器选择质量如何？"**

> 降级不是说随便选。候选池在进来之前已经按综合评分排过序了，降级只是取 top-N——本质上是"如果没有 AI 精选，就按规则引擎的评分顺序来"。用户看到的是"系统按数据匹配度自动选择"，对终端用户来说是透明的。

**Q: "有没有 AI 返回了正确的 JSON 但推荐质量很差的场景？"**

> 有。比如 AI 返回了 3 个候选但全是同一个城市的，不够多样化。目前 diversity trim 只在候选池构建阶段做，未来可以加一层"AI 返回结果多样性校验"。这也是为什么 blocked 列表要持久化——方便后续审计和迭代。

## 四、CompletableFuture 并行 + SSE 流式

**简历原文：**
> 基于 CompletableFuture 并行执行三档推荐任务，结合 SSE 流式推送优化生成链路，推荐生成耗时由 60s+ 降至约 15s；引入 Redis 状态机与分布式锁管理长任务生命周期，支持断点恢复与重复提交拦截。

### 技术实现

**并行执行：**

```java
// DraftServiceImpl.java
List<CompletableFuture<TierResult>> futures = new ArrayList<>(3);

for (WorkspaceTierVO wsTier : wsTiers) {
    CompletableFuture<TierResult> future = CompletableFuture
        .supplyAsync(() -> {
            AiSelectionResult sel = aiSelectorService.select(tier, candidates, score);
            return mergeSelection(rawTier, sel);
        }, threadPoolTaskExecutor)  // 自定义线程池 50-200 线程
        .orTimeout(90, TimeUnit.SECONDS)  // 兜底超时
        .exceptionally(ex -> fallbackTierResult(...)); // 异常降级
    futures.add(future);
}

// 按顺序收集结果（reach → steady → safe）
for (CompletableFuture<TierResult> future : futures) {
    TierResult tr = future.join(); // 阻塞等待，但不抛异常（exceptionally已兜底）
    // 逐档持久化+推送 SSE
}
```

**耗时分析：**

```
串行（旧）: reach 15s → steady 15s → safe 15s = 45s + DB 10s = 55s+
并行（新）: max(reach, steady, safe) = 9s + DB 5s + SSE 1s = 15s

模型切换: deepseek-v4-pro → deepseek-v4-flash
单档耗时: 15s → 3s
总耗时: 15s → 5s (并行后为最长单次)
```

**SSE 双通道：**

| | 草稿生成 | AI 对话 |
|---|---|---|
| 传输 | EventSource GET | fetch POST ReadableStream |
| 鉴权 | 短期 streamToken（URL 参数） | Authorization Header |
| 事件 | progress / done / error | token / tool_call / done / error |
| 设计原因 | EventSource 不能带 Header，改用 token | 需要 POST 消息体 + Bearer token |

**Redis 状态机：**

```
DraftGenerationTaskState (Redis: ai:v2:draft:task:{taskId})
├── status: running → done / error
├── phase: profile_analysis → filter_408 → candidate_pool
│         → ai_selecting → validate → finalize
├── streamEventsJson: 累积事件列表（前端轮询拉取）
├── tierJson: 逐档实时数据（前端增量渲染卡片）
└── draftJson: 最终草稿（done 事件时填充）

前端轮询: 每秒 GET state → 对比 signature → 有变化则推送 SSE
断线恢复: onMounted 时检查 draft 状态，若 generating 则轮询 GET /draft 直到完成
```

**分布式锁：**

```java
// 生成锁 — 防重复点击
String lockKey = "ai:v2:draft:lock:" + userId;
Boolean locked = redis.opsForValue().setIfAbsent(lockKey, lockValue, Duration.ofMinutes(10));

// 释放 — Lua 脚本原子校验 value 匹配（防误删他人锁）
String script = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";

// 对话锁 — 防并发发消息覆盖历史
String chatLock = "ai:v2:chat:lock:" + userId;
if (!redis.setIfAbsent(chatLock, "1", 60s)) {
    callback.onError("上一条消息仍在处理中");
}
```

### 面试话术

> "性能优化的核心思路是并行化。原来三档 AI 选择是串行的——冲刺档选完了才开始稳妥档，稳妥档选完了才开始保底档。每档调一次 DeepSeek 大概 15 秒，三档加起来 45 秒，加上数据库查询和校验，用户要等将近一分钟。
>
> 我改成了 CompletableFuture 并行执行——三档同时发请求，耗时等于最慢那一档。然后用 orTimeout 设了 90 秒兜底，exceptionally 做降级处理。线程池也从 ForkJoinPool 换成了自定义的 ThreadPoolTaskExecutor，因为 AI 调用是 IO 密集型，需要大量线程同时等待网络响应，ForkJoinPool 的 7 个线程根本不够。
>
> 前端方面用了 SSE 流式推送，第一档 AI 选完就推到前端渲染卡片，用户不用等所有档都完成。配合 Redis 状态机，用户刷新页面或者断线重连都能恢复到当前进度。"

### 追问应对

**Q: "为什么要自定义线程池而不是用 ForkJoinPool？"**

> ForkJoinPool 设计用于 CPU 密集型任务的 work-stealing，线程数等于 CPU 核数（通常 4-8 个）。但 AI 调用是 IO 密集型——线程大部分时间在等待网络响应，不是在做计算。8 个线程全部阻塞在等 DeepSeek 返回时，其他请求就排不进去了。改成了 ThreadPoolTaskExecutor，core=50/max=200，有界队列 1000，拒绝策略 CallerRunsPolicy（队列满时由调用线程执行，形成反压）。

**Q: "SSE 两种通道的设计区别？"**

> EventSource 浏览器 API 只能发 GET 请求，不能带自定义 Header。所以草稿生成的鉴权不能走 Authorization Header，而是改成了短期 streamToken——先 POST 获取 token，再用 EventSource GET 订阅。AI 对话因为需要 POST 发送消息体，所以不用 EventSource，而是 fetch + 手动解析 ReadableStream 的 SSE 格式。

## 五、Agent 工具体系

**简历原文：**
> 基于 LangChain4j Tool Calling 构建 Agent 工具体系，将院校检索、数据对比、方案调整等能力封装为 12 个工具，实现推荐方案的自然语言查询、分析与调整，形成"对话 + 工作台"双交互模式。

### 技术实现

**12 个工具分类：**

| 类别 | 工具 | 作用 |
|------|------|------|
| **检索（5个）** | `searchPrograms` | 搜索学校（DB 查询，支持地区/层次/分差过滤） |
| | `getDraftContext` | 获取当前草稿快照（三档候选+理由+风险） |
| | `getProgramDetail` | 查看学校详情（分数线/名额/趋势） |
| | `comparePrograms` | 对比两所学校 |
| | `getRefillCandidates` | 查看补位候选列表 |
| **原子修改（3个）** | `addDraftCandidate(programId,tier)` | 添加候选（workspace→DB fallback） |
| | `removeDraftCandidate(programId)` | 移除候选（自动触发 refill 策略补位） |
| | `confirmRefillCandidate(programId)` | 确认补位候选 |
| **批量操作（4个）** | `fillTier(tier)` | 填满指定档位（AI 指定档位，后端自动选候选） |
| | `replaceDraftCandidate(removeId,addId)` | 原子替换（移除+添加，不触发 refill 双重效应） |
| | `batchReplaceDraftCandidates([...])` | 批量替换（每项独立校验，部分失败不阻塞） |
| | `batchRemoveDraftCandidates([id1,id2])` | 批量移除 |

**写互斥机制：**

```java
// V2DraftActionTools.java — 每个写工具的第一行
if (V2ChatToolContext.writeExecuted()) {
    return error("write_already_executed", "Write already executed this turn.");
}

// 设计意图：
// AI 可以在一次回复中调用多个工具，但写操作只允许一次
// 避免"移除+refill补位+替换+填充"四重连锁效应导致结果不可预测
// 复合操作用专用工具承载（replaceDraftCandidate = 移除+添加的原子操作）
```

**工具调用线程模型（ThreadLocal Bug 故事）：**

```
Tomcat HTTP 线程
  → V2ChatToolContext.init(userId, ...)  // ThreadLocal.set(context)
  → assistant.chat(message).start()
  → DeepSeek 返回 tool_calls
  → OkHttp dispatcher 线程: callWith(context, tool) // 暂挂到工具线程执行
  → OkHttp 回调线程: onCompleteResponse
       V2ChatToolContext.draftChanged()  // ThreadLocal.get() → null!
       ↑ BUG: 跨线程丢失
  → 修复: toolContext.draftChanged()   // 直接读捕获的对象引用
```

**对话 + 工作台双面板：**

```
┌─ 左侧配置栏 ─┐  ┌─ AI 对话区 ────────────┐  ┌─ 右侧草稿面板 ────┐
```

### 面试话术

> "Agent 最大的坑是工具副作用失控。LangChain4j 允许 AI 在一次回复中调用多个工具，如果你不加限制，AI 可能会先 remove 一个、自动 refill 补了一个、再 replace 一个、最后 fillTier 填到上限——四个操作互相干扰，最终草稿变成什么样子完全不可预测。
>
> 我的做法有两层约束。第一层是写互斥：单轮对话只允许一次写操作。第二层是复合操作用专用工具承载：比如 replaceDraftCandidate 是一个原子操作，内部同时做移除和添加，但它跳过了移除操作自带的 refill 策略，保证不会多出一个候选。
>
> 工具还做了权限分层——读工具随时可用，原子修改有互斥锁，批量操作对每个 item 独立校验，一个失败不影响其他。AI 只能说'做什么'，不能说'怎么做'。"

### 追问应对

**Q: "为什么不直接让 AI 输出 JSON 动作而不是 Tool Calling？"**

> Tool Calling 的优势是结构化约束。AI 输出 JSON 你需要自己做意图识别、参数校验、错误处理，而且 prompt injection 风险更高。LangChain4j 的 Tool Calling 框架已经在 schema 层做了参数类型校验，工具执行结果回传给 AI 形成闭环，AI 可以说"已替换成功"而不是猜测是否成功。

**Q: "ThreadLocal 那个 Bug 怎么发现的？"**

> 现象是 AI 对话中修改了草稿，后端日志显示草稿确实变了，但前端面板不刷新——因为 `draftChanged` 一直是 false。加了日志发现 `V2ChatToolContext.draftChanged()` 返回 false，但 `writeExecuted` 明明是 true。进一步排查发现 `draftChanged()` 走 ThreadLocal 读取，而 `onCompleteResponse` 回调在 LangChain4j 的 OkHttp 回调线程上执行，ThreadLocal 在那个线程上是空的。修复方案是不从 ThreadLocal 读，而是用 Java 闭包捕获的 context 对象引用直接读字段。

## 六、候选综合问题

### "这个项目最大的技术挑战是什么？"

> AI 可信度治理。让用户信任 AI 的推荐——不仅仅是"AI 说这所学校好"，而是"这所学校的数据支撑它好"。
>
> 技术上的解决方案是三层：第一层是候选池约束——规则引擎预先筛选，AI 不能从 400 所学校里瞎选。第二层是 5 层校验——AI 返回的每个推荐都要过五道关卡。第三层是降级——AI 挂了也不影响用户体验，自动回退到机器评分。
>
> 最难的不是写代码，是设计这整套防御体系——你不知道 AI 会以什么方式出错，但你必须假设它一定会出错。

### "如果让你重新设计，你会改什么？"

> 候选池构建和 AI 选择之间的数据流。目前 Workspace 是草稿生成时的一次性快照，存在 Redis 里。如果用户在对话中修改了偏好（比如把地区从福建改成广东），Workspace 不会自动重建，AI 的候选池还是旧的福建学校。应该设计成 Workspace 可以根据偏好变化动态重建，或者至少有一个触发重建的机制。

### "项目上线了吗？用户反馈是什么？"

> 部署在自己的云服务器上（408lab.site），Demo 阶段，自己使用和演示。目前的发现是：AI 对保底档的推荐比较保守（因为保底需要分数明显高于录取线，在特定地区可能真的找不到），这个不是 bug 是数据现实。速度方面，换了 Flash 模型后从 60 秒降到 23 秒左右，体验上感知很明显。
